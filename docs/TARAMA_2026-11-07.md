## Priority 1: bugs proven offline, small and safe fixes

### 1. Our fixed old User-Agent ruins impersonation (affects every site, curl_cffi included)
- **Evidence:** `fetch.UA` = `Chrome/130` (from 2024). `_ytdlp_opts` always sets `http_headers={"User-Agent": UA}`. With impersonation, yt-dlp only strips its *own* std_headers and lets curl_cffi supply a matching UA (`yt_dlp/networking/impersonate.py` 132-148, `_get_impersonate_headers`). Our UA is not equal to std_headers, so it stays.
  `ua_test.py` output:
  `custom UA -> ...Chrome/130.0.0.0... | target: chrome-152:windows-10`
  `default   -> None | target: chrome-152:windows-10` (curl_cffi adds its own consistent UA)
  So we send a Chrome 152 TLS/HTTP2 fingerprint with a "Chrome/130" UA. That mismatch is the kind of thing Cloudflare and Dailymotion-style bot checks look for. The same happens in `_http_get` (curl_cffi `impersonate="chrome"` + UA header) and in `ytdlp_download` when `headers` is passed (`{"User-Agent": UA, **headers}`).
- **Fix:** do not set a User-Agent in `_ytdlp_opts` (yt-dlp's own `random_user_agent()` is Chrome 145-151, `utils/networking.py:17`). In `ytdlp_download`'s `headers` branch, pass only Referer. In `_http_get`, drop User-Agent when curl_cffi is used. For the ffmpeg/requests paths, `UA` can come from `yt_dlp.utils.networking.random_user_agent()`, which yt-dlp keeps current.
- **Risk:** low. Tests that check UA in headers may need updating.

### 3. URL forms that are "Unsupported" or broken in yt-dlp: normalise before downloading
`match_test.py` output (which extractor accepts the URL in yt-dlp 2026.10.26):
- `https://m.ok.ru/video/<id>` -> **generic** (Odnoklassniki `_VALID_URL` only allows `(?:www\.)?`). Also `ok.ru/group/<g>/video/<id>` and `ok.ru/profile/<p>/video/<id>` -> generic (I could not confirm these forms occur in the wild).
- `https://rutube.ru/shorts/<32hex>/` -> **generic** (`rutube.py:113`; the RutubeChannel IE does have a `shorts` section, so shorts exist). That the id is the same as `/video/<id>/` is a likely guess, **not verified**.
- `vk.com/video_ext.php?oid=..&id=..` (embed form) -> VK IE accepts it, but **that code path is broken**: `vk.py:470` looks for `var playerParams`, and VK changed the embed page ("Unable to extract player params", #16070 and #17537 (2026-08); fix PR #16066 still unmerged). #17537 notes that **the page form `https://vkvideo.ru/video-OID_ID` works for the same video**.
- **Fix:** add `site_url_variants(url) -> list[str]` in `fetch.py`, used in `_ytdlp_to_wav` / `ytdlp_download` (and in the `embed()` step, because `find_embeds` collects `vk.com/video_ext` iframes and these currently fail):
  - `m.ok.ru` / `*.ok.ru/.../video/<digits>` -> `https://ok.ru/video/<digits>`
  - `rutube.ru/shorts/<id>` -> `https://rutube.ru/video/<id>/`
  - `vk(video).ru|vk.com/video_ext.php?oid=X&id=Y[&hash=H]` -> try `https://vkvideo.ru/videoX_Y` first, then the original embed URL (videos embedded with a private hash may only open through the embed).
  The variant is tried first. If it gives a non-transient error, the original URL is tried. The original URL is kept in `webpage_url` / the record (`sources.normalize_url` already strips `m.` from the key, so duplicate detection is unaffected).
- **Risk:** low to medium (per-site regexes). Tests: pure string tests.

### 4. ok.ru: try the `videoembed` form as a second try (for clearer errors and some videos)
- **Evidence:** the current extractor (`odnoklassniki.py` 222-242) downloads `ok.ru/{video|videoembed}/<id>` and raises an `ExtractorError` with the message shown in the `vp_video_stub_txt` element. Issue #15845: for a region-locked video the desktop page gives "Unable to extract player", while `ok.ru/videoembed/<id>` shows "not available in your country". So the embed form at least gives a real reason, and for some videos it may play.
- **Fix:** if an ok.ru URL fails with "unable to extract player" (no cookies, then impersonation), try `https://ok.ru/videoembed/<id>` once. If that also fails, show the embed error (the ok.ru message, translated) to the user as the main error.
- **Risk:** low. One extra request. **Not live-tested** (network blocked).

### 5. A collection URL not caught by `is_collection_url` downloads the whole channel
- **Evidence:** `noplaylist=True` only takes effect in extractors that call `_yes_playlist` (dailymotion.py:410). VKUserVideos, RutubeChannel, DailymotionUser and others ignore it. `ytdlp_download` calls `extract_info(url, download=True)`: every entry is resolved and downloaded to `kaynak.%(ext)s`, and the first one is then picked (`fetch.py` 413-418). For a 1000-video channel that is a very long wait and risks a rate limit.
- **Fix:** add `"playlist_items": "1"` to the options in `ytdlp_download` only (not in `_ytdlp_opts`, because `ytdlp_info(flat)` in channel listing uses `playlistend`).
- **Risk:** low.

## Priority 2: better fallbacks (medium effort)

### 7. Browser capture (`browser.py`): cookies and UA
- `capture_media` joins *all* cookies of the context into one Cookie header, and `_media_headers` sends it to every media URL. That leaks cookies across domains. On ok.ru it may also break the download: the yt-dlp source says "Direct http downloads will fail if CDN cookies are set" (`odnoklassniki.py` 211-215, `_clear_cookies`). **Fix:** take cookies per candidate URL with `ctx.cookies([candidate_url])` before the browser closes, and give each candidate its own Cookie header.
- The context is a fresh profile, so for VK/ok.ru videos that need login, capture cannot help either. **Fix (legitimate, uses the user's own cookies):** load the Netscape file that `browser_cookie_file()` already produces into the Playwright context with `ctx.add_cookies` (only cookies for the page's domain and its subdomains). Risk: medium (cookie format conversion, expiry and SameSite fields).
- `new_context(user_agent=UA)` puts "Chrome/130" on top of the real Edge (version 14x). Client Hints (Sec-CH-UA) and the UA then disagree (I believe so; **not verified**). **Fix:** build the UA from `browser.version` (`...Chrome/{major}.0.0.0 Safari/537.36 Edg/{major}.0.0.0`), which also hides "Headless".

### 8. Daily yt-dlp update: consider the nightly channel
- **Evidence:** the yt-dlp README (METADATA line 243-265): "the latest stable release is often stale and prone to external breakage ... nightly is the recommended channel for regular users", and it is installed with `pip install -U --pre`. Example: the ok.ru break of September 2026 (#17698/#17710, "the JSON object must be str...") was fixed by PR #17739 (merged 2026-09-27), but stable only shipped it on 2026-10-21. Users on stable could not download from ok.ru for about 3.5 weeks.
- **Fix:** `start_ytdlp_update` -> `pip install -q --upgrade --pre "yt-dlp[default,curl-cffi]"`. Add a setting (`ytdlp_nightly = true`) to turn it off. A safer variant: stay on stable normally, and install nightly only when an "Unable to extract / extractor error" appears (next start).
- **Risk:** medium. A nightly can occasionally regress, and `--pre` also lets pip pick pre-releases of curl_cffi and other dependencies. To limit it to yt-dlp, install in two steps: first `pip install -U "yt-dlp[default,curl-cffi]"` (stable dependencies), then `pip install -U --pre --no-deps yt-dlp`. This needs to be decided and tested; whether pip on Windows overwrites the package while files are in use was not tested.

### 9. Check that impersonation is really available
- `impersonate_target()` only checks `import curl_cffi`. yt-dlp supports only curl_cffi 0.10.x-0.17.x (`networking/_curlcffi.py:36-38`). With another version yt-dlp does not register the handler, and **every** cookie attempt fails with `Impersonate target "chrome" is not available` (`YoutubeDL.py:767-771`), because cookie attempts carry `impersonate` too. The pip extra pins the right range, so the probability is low (only if some other package pulls in a newer curl_cffi).
- **Fix:** check with `from yt_dlp.networking._curlcffi import CurlCFFIRH` (it raises ImportError on a version mismatch), or with `YoutubeDL()._impersonate_target_available(...)`. When it is not available, do not add `impersonate` to cookie attempts.
- **Risk:** low.

### 10. mail.ru: add the meta URL in the page as an embed
- **Evidence:** `mailru.py:105-131`. If the page config (`sp-video__page-config`) is not found, `meta_url=None` and `re.match(..., None)` raises a TypeError (#15243). The extractor accepts `my.mail.ru/+/video/meta/<id>` and `my.mail.ru/video/embed/<id>` directly, without the page (the `metaid` branch).
- **Fix:** in `find_embeds`, add these patterns from the page HTML (`og:video` content is often `my.mail.ru/video/embed/<id>`; `"metaUrl":"/+/video/meta/<id>"`). Add `my.mail.ru/video/embed` and `/+/video/meta/` to `_EMBED_HOSTS`. Generalisation: if a URL in `og:video` / `twitter:player` matches a known embed host, send it to the "gömülü" (embed) step through yt-dlp instead of straight to ffmpeg.
- **Risk:** low. **Not live-tested.**

## Priority 3: notes, no code change needed or not recommended
- **Dailymotion:** yt-dlp since 2026-01 (#15526/#15697/#15995) tries the m3u8 with "randomized headers -> chrome -> firefox impersonation" (`dailymotion.py:366-395`, `require_impersonation=True`). So curl_cffi is *required*. The app already installs `yt-dlp[default,curl-cffi]` (pyproject.toml:13, and the daily update). The current chain is right. Open PR #17640: an embed regex bug for iframes without quotes (TypeError on pages like franceinfo, #17574). We cannot fix that ourselves (our `_IFRAME_RE` also wants quotes).
- **VK:** besides the embed form (item 3), page form + no login is affected by "Video only available to followers" (#17608, open, not fixed with cookies) and possibly a broken anonymous path (PR #18002 "Fixed anonymous video extraction for vkvideo.ru", opened 2026-11-05, unmerged; its description is empty, so the scope is unknown). The way out today is browser capture (VK plays as DASH/HLS in the page) and the user's own VK cookies (item 7).
- **Rutube:** PR #17513 (`no_404`, `referer` parameters) and #17579 (surface site errors) are unmerged. Until they land, the 404 explanation (item 2) and browser capture are enough. Doing our own `rutube.ru/api/play/options/<id>/?no_404=true` call only gets the error *reason* (the site's own public player API). Optional.
- **Geo-blocks (`geo_bypass` / X-Forwarded-For / proxy):** yt-dlp's default (`geo_bypass=True`) is enough. The app should not add a VPN/proxy feature; it should only explain the cause clearly in Turkish.
- **Generic sites behind Cloudflare:** the global `impersonate` parameter also reaches the generic extractor (the handler's default target applies to every request; checked in `YoutubeDL.py` ~4365 `'impersonate': 'impersonate'`). So the "tarayıcı taklidi" (impersonation) attempt already covers this. Once the UA fix (item 1) is in, it gets more effective.
- Other "similar sites" extractors exist and are maintained: dailymotion(+user/playlist), Odnoklassniki, mailru, vk(+uservideos, wallpost), VKPlay/VKPlayLive, rutube(+channel/playlist/person/embed), dzen.ru, BiliBili/BiliIntl, Vimeo (some videos need login; uses impersonate), Streamable, Rumble(+channel), Kick (impersonate required), TwitchVod, Twitter/X, TikTok (impersonate), Facebook, Instagram (instagram:user marked "CURRENTLY BROKEN"), Coub, Smotrim, PeerTube. Sibnet only through embeds (`video.sibnet.ru/shell.php` goes to generic).
- DRM: unchanged. `_check_manifest_drm` and `is_drm_error` are adequate. None of the proposals touch DRM.
- Third-party "downloader" sites: none suggested.
